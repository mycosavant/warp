Own Credentials, All the Way Down

The maintainer lives in the Windows build and logs frictions. In parallel, the agent works this board: the thesis names local models and nothing has ever answered the panel from this machine; the protocol reaches four agents and one is measured. Every item here can be built and measured without the maintainer at the desk, except where a gate says otherwise.

What this is and is not

A second horizon beside GOAL.md, not a replacement. Live in it stands until seven working days are logged; its rule that a friction which stops a turn is fixed the same day outranks every row below. This page is what the agent does on the days nothing stopped. It is a run with a definition of done, so it can be met or abandoned and then deleted.

Done when: a turn in the panel is answered by a model running on this machine, with the event log naming it and zero sockets off loopback during the turn (met 2026-09-09, except that the last clause was true of Warp and false of the agent — see item 3); the picker has been measured against a list that is not Anthropic's; every agent in the survey table is filled from the wire or blocked on a credential the maintainer has declined; and the specs card says something true about every row on offer, including ?.

A local model answers the panel

done 2026-09-09
the thesis, measuredrun: .fork/runs/localmodel-panel-2026-09-09/

Three of the four criteria hold; the fourth fired the falsifier below, and that is the result. Gemma 4 12B on llama-server answered the panel through claude-agent-acp with no fork code written. session_model, the agent's own harness transcript and the footer chip all name gemma-4-12b, and warpctrl agent trace carries all three in eight lines. The tool-call falsifier did not fire: the model ran a shell command and quoted its output back correctly. What did fire is the socket census. Warp made zero non-loopback connections for the whole run — three listeners and nothing else. The agent's process opened four TLS connections to api.anthropic.com on every turn, before it opened the one to the model, and CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 does not remove them. Bounded by volume, since TLS cannot be read: 254,858 bytes to loopback against 9,286 bytes up and 171,451 down to Anthropic — so the prompt went local and something else did not. This is the gap CLAUDE.md already names in one sentence, now measured: the deny-list is Warp's HTTP client, and the agent is not behind it. Closing it is a firewall rule, not a warpctrl change. The thing that nearly stopped the run was not the model: serve.ps1 defaults to 12,288 tokens of context and this repository's CLAUDE.md is ~42,000 tokens of every request, on top of Claude Code's own 20,860-token floor. -Ctx 98304 fits in 12 GB because Gemma's sliding-window attention costs ~16 MiB per 1k tokens.

Two agents can do this without a line of fork code. opencode speaks to an OpenAI-compatible endpoint from its own config. claude-agent-acp honours ANTHROPIC_BASE_URL, and llama-server's /v1/messages answered the Anthropic shape correctly on 2026-09-07, so the recommended agent keeps every permission measurement this fork has made and swaps only the model. Either way the panel path is unchanged: WARP_FORK_ACP_COMMAND names the same agent and the agent names the runtime. What is measured is the claim the fork makes in its first sentence: one turn, the event log's session_model line naming the local model, the harness transcript agreeing, and a socket census during the turn showing loopback and nothing else. The specs table gets a row with output = 0, so the cost bar is empty for the one honest reason.

Falsifier
  • FIRED. A socket to a provider during a local turn. Not OpenRouter and not opencode — claude-agent-acp to api.anthropic.com, four connections per turn, opened before the model's. Warp itself: loopback only.
  • Did not fire. The tool calls worked: the model ran echo and quoted the output back. One step, on a 12B; nothing here says it holds for a long multi-step turn.

The specs card for a list the table cannot hand-cover

done 2026-09-09
T21.4run: .fork/runs/pricefetch-2026-09-09/

Four rows were written by hand from the vendor's page. Item 1 puts hundreds on offer, and a table cannot follow them. OpenRouter's public model list carries a price per row and needs no key, so the fetch the ticket parked earns its place here: opt-in, off by default, one request per launch at most, cached under the state directory with its age in days printed on the card, and refused by name unless the variable is set. It is the first host Warp's own HTTP client dials by Warp's own choice — an earlier version of this line said “a party that is not the person's own agent”, which reads as a claim about the whole machine and is false, since the agent's process dials plenty. That is why it is a variable and not a default, and why the egress deny-list is not the layer that decides it.

Measured: 430 rows, 58 vendors, no key. The fetched prices match all four hand-written rows exactly, two days after a person typed them off the vendor's page. Three live-data facts changed the code: five openrouter/* auto-routers quote -1 where 21 other rows quote a real 0, so a negative is dropped and zero is kept; every anthropic/* slug has a :batch twin at half price one colon away, so the lookup is exact-match; and prices arrive as per-token decimal strings.

And reading the client turned up a disclosure the diff would not have shown. http_client::Client::get attaches the client id, the app version and four OS fields — down to the kernel version — to every host, because include_warp_http_headers is unconditionally true off wasm. In this fork the app version is v0.fork.<sha>. get_without_warp_headers is the fix; it still goes through execute_inner, so the egress policy sees it.

Falsifier
  • Did not fire. The fetch runs with the variable unset. Plan::of returns Off across every cache state, and a second test pins that the module builds exactly one HTTP client and that it sits behind that decision — because the first pins the decision and only the second pins that there is nowhere else to ask from. Calibrated by failing: its first version counted the module doc that names the method it checks.
  • FIRED, as designed. An OpenRouter slug that does not map to the agent's id: opus against anthropic/claude-opus-5, and no rule derives one from the other. That is why the table names the slug and the fetch only fills its numbers. An unknown slug falls back to the row's own figures, so switching the fetch on can add a price and cannot remove one.

The instrument was wrong first, again. The 15,587 and 14,975 figures on record are the same build read by a 10-second sampler — adjacent ticks near the peak swing 1.7 GB. The exact number comes from /usr/bin/time -v, which has no sampling window, calibrated three levels deep against a known 700 MB allocation. Two identical baselines then agreed to 6 MB with byte-identical binaries, which is the only reason the two small levers are readable at all.

It cannot be an environment variable, and the failure is silent. CARGO_PROFILE_RELEASE_PACKAGE_warp_DEBUG=0 is ignored with no error — rustc still gets -C debuginfo=1. The whole-profile form works and reaches every crate, so toggling it costs a full rebuild. The setting lives in Cargo.toml, beside the [profile.dev.package] block already there.

And the profile is still not the largest lever. The same crate had 22,795 MB of headroom with no rust-analyzer resident and 8,198 MB with one. Killing an editor's language server is worth 14.6 GB — three times this whole sweep.

kode-rs as a third harness

recon done 2026-09-09 · the maintainer's call
raised by the maintainer~/dev/kode-rs, HEAD 7c0cbc5, 2026-08-10

“Another point of infra that we own.” The fork's seam is agent-agnostic on purpose — WARP_FORK_ACP_COMMAND names a command and that is the whole switch — so a third agent costs no Warp code, and this one is the maintainer's own.

Its ACP side is real and on the main branch, not only in a worktree: crates/kode-engine/src/acp.rs, 1,176 lines, a 210-line protocol test and a design doc. Hand-rolled v1 subset, no agent-client-protocol dependency, exposed as kode-engine acp. It handles initialize, session/new, session/prompt and session/cancel, and sends session/update and session/request_permission — the last being the one the fork's consent surface actually needs.

What it does not have decides how much of this fork it lights up, and its own design doc is explicit about the omissions: no session/load, no authenticate, no fs/*, no mode or config-option updates. So permission requests would reach the panel and a paired phone; WARP_FORK_ACP_MODE would have nothing to set, which is fine because unset sends nothing; and the model chip is dead — no configOptions, no session/set_config_option. The specs card would draw ?, which is what it is for. It already carries kode-models/openrouter_catalog.rs and pricing.rs, so it solved item 4's problem on its own side, independently.

Not built and not run. A month stale, 58 GB on disk mostly target output, and the OpenAI Codex angle the maintainer raised alongside it (first-class third-party providers, likely better UX than opencode) is a separate question about which agent to name, not about Warp. The honest summary: the two missing methods are exactly the two the fork's newest work depends on, and both are small additions to a file that already speaks the protocol.

Before this becomes work
  • Does it still build? A month stale against a moving toolchain is unmeasured.
  • Which question is being answered — “an agent we control end to end” or “a better agent than opencode”? Codex answers the second and not the first.

The clean-build test of -j 8

a quiet hour
GOAL standing constraint30+ minutes, carries the risk it measures

Two sampled builds measured the tail of the graph, where the app crate compiles alone at 15 to 17 GB, and neither was the many-large-crates front that took the guest down. The cap is unresolved, not lifted until a clean build is sampled the same way. It runs only when the maintainer says no Windows build is running, because the host's 64 GB is the quantity that matters and both sides draw on it.

Attempted 2026-09-09, stopped part-way, and it is more open than before. target/release was wiped and the build started; two things went wrong. The sampler was counting rust-analyzer as a compiler — ps -C rustc is not an exact match on this procps, and a rust-analyzer over this workspace holds 15–16.5 GB. Corrected, the same moment read 2–3 GB across seven compilers, heaviest 847 MB.

The corrected sampler then reached the app crate before the build was stopped, and it mostly answers this item. The -j 8 front — seven concurrent compilers — peaked at a summed 3,287 MB, heaviest single 911 MB. The warp crate then compiled alone, climbing to 14,975 MB and still rising when killed. So the 15–17 GB figure above is confirmed, not suspect — and the doubt raised here an hour earlier was wrong, since a rust-analyzer reports ? for its crate and that sample named warp. The real finding is the shape: MemAvailable bottomed at 8,198 MB while exactly one compiler was running, against 19,300 MB through the parallel phase. -j 8 is not what stands between this build and the wall, and no value of -j would be.

And the build should not have started: the check run was free -m inside the guest, which said 22 GB available, while the host was at 60 GB of 64. The maintainer caught it. The precondition is now three things: read the host with powershell.exe Get-CimInstance Win32_OperatingSystem, kill the guest's own residents first (a 15 GB language server is a confound, not just pressure), and account for llama-server's permanent 10.2 GB.

What this now has to answer
  • The clean-build peak, on a corrected sampler — the original question.
  • An uncapped front half. That is now the only part still unmeasured: eight jobs averaged ~470 MB each, and what thirty-two of them do together is the question the cap was actually chosen for.
