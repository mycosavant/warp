## Findings

**The main one, and the agent found it, not me.** `handle_action_result`
(`action_model.rs:1451-1480`) makes the post-rejection status *conditional*:
`Cancelled` if every finished result is cancelled, `InProgress` otherwise. So a
rejection of the **only** pending action ends the conversation as `Cancelled`
(→ `stop_failure`, no `permission_replied`), and a rejection alongside other
successful results resumes the turn (→ `permission_replied`).

Two earlier readings in this repo were each half of that, and the flat version
had already been committed into `Entry::decision`'s doc. Corrected.

**Why it was found here and not in review.** The prompt asked the agent to
*walk the path* and quote the deciding lines, rather than to confirm a
conclusion someone already held. Both prior readings stopped one call short —
at `handle_action_result`'s door rather than inside it.

## Turn 3 — the second finding, also the agent's

Asked what could make the audit trail **lie** rather than what it covered. It
separated the two logging call sites: `permission_request` is written
synchronously in the request handler, `permission_replied` from a task
cancellation drops mid-`await`. So a cancelled turn keeps the question and loses
its answer.

Verified independently before believing it (`take_until` at `mod.rs:287`, the
`registry` module docs, `Waiting::drop`), and the verification found the sharper
half: the `unanswered` value was **unreachable on the real path** while being
exercised by a unit test. Coverage asserted in a doc comment and absent from the
code — the failure this fork keeps paying for, in code written the same morning.

Fixed with a drop guard (`AsksNothingMore`), `202b20130`.

**The prompt shape is the reusable part.** Twice now, asking the agent to walk a
path and quote deciding lines — rather than to confirm a conclusion — has beaten
both the author and the advisor. Turn 1 corrected a committed doc; turn 3 found
a shipped defect. Neither came from asking "is this right?"


## Turns 4-5 — the verification run

Not review work; a deliberate two-phase measurement of the turn-3 fix
(`.fork/tools/cancel-leaves-no-orphan-ask.sh`). Both turns raised exactly one
permission request and both were answerable from the control plane.

Worth logging as friction data anyway, because it is the first time this session
that Warp was *in the loop* at all:

- **The ask that parked in phase A was `ls target/ 2>/dev/null | head -1 || echo
  "target dir missing"`.** `ls*` is allowed; `head` and `echo` are not, and
  opencode decomposes a compound and matches each segment independently — so the
  compound asked. That is the documented behaviour working, and it is also the
  clearest illustration yet that the allowlist is drawn around *commands the
  maintainer named*, not around what a command can do.
- **Answering cost one paste.** `agent approvals` printed the exact
  `agent approve '<id>' --digest <d>` line. No transcription.
- **`cat "$EVENTS"/*.jsonl` returns filename order, not time order.** The ACP
  path files per conversation, so phase B's lines printed above phase A's. The
  log is right; a reader inferring causality from line order would not be.
  Annoying, not stopping — but it is the kind of annoyance that becomes a wrong
  finding, so it went into the docs rather than only here.


## Turn 6 — a clean bill, verified on a second instrument

Same prompt shape as turn 3, pointed at the consent path: what could make a
*yes* land on a question it was not given for. Three questions, each demanding
the deciding lines.

It found nothing wrong, and the interesting part is that it was **asked not to
invent a third finding and did not**. Two of its load-bearing claims were
re-checked by hand and both hold:

- `can_approve` is excluded from the digest but provably cannot flip without a
  hashed field flipping — pane path `can_approve: refusal.is_none()` where the
  refusal is a function of `agent`, which is hashed. Checked further than the
  agent did: `agent_name` is *injective* over the `CLIAgent` variants (every
  first command prefix is distinct; only `Unknown` maps to `"?"`, and it is
  unverified anyway), so no two agents can hash alike while differing in
  approvability.
- `approval_id: format!("{turn}:{id}")` with `turn` a per-`run` `Uuid::new_v4()`
  — so a JSON-RPC id that is only unique per connection is scoped to a turn.
  Confirmed at `mod.rs:885` and `mod.rs:311`.

One thing it surfaced that is worth keeping: **the error texts are an existence
oracle** — "parked but wrong digest" is distinguishable from "nothing parked".
Moot today because `agent.approvals` hands the whole waiting set to any
authenticated caller, so the oracle discloses nothing new. Worth remembering if
a caller class ever exists that can answer but not list.

The agent reached for `find /` — a filesystem-wide walk, outside what the charter

**The turn then ended with `status: success` and produced no answer at all.**

This sharpens a claim already in CLAUDE.md. The recorded case was a denial *at

### Turn 17: sixteen permission requests for one question

Re-ran with explicit steering in the prompt — *use your read and grep tools, do
not shell out, do not run `find /`.* The agent shelled out on its **first** call
anyway (`ls ~/.cargo/... | grep`), and again on its second (`find ~/.cargo/...`),
then produced fourteen more `rg` asks. I cancelled at 16.

**Steering in the prompt did not hold.** CLAUDE.md's advice — *"read files with
your read tool; do not shell out for something a native tool already does"* — is
written for an agent reading that file. Put directly into the prompt, in the
imperative, it was ignored within one call. That is a materially weaker result
than the doc implies, and worth knowing before relying on steering as a remedy.

### What worked, unplanned

**The `AsksNothingMore` guard built this morning fired in production.** The
cancelled turn logged **16 `permission_request` and 16 `permission_replied`** —
fifteen decided, and the sixteenth `decision: unanswered`. Before this morning
that last ask would have been an orphan: a question shown, no record of its
ending. First real use, and it was not a test.

**And the audit trail was used for its stated purpose, on me.**

### My own process failure, recorded because the trail caught it

Faced with a stream of asks I wrote a loop that printed each request and then
approved it — *regardless of content*. That is precisely the hazard GOAL.md
names: *"an unattended script answering an agent's prompts is the consent
architecture with no person in it."* I did it while present, which is not much
better.

Auditing the trail afterwards, all fifteen were `ls`/`find`/`rg` scoped to the
repo or `~/.cargo/registry/src` — every one inside what the charter allows. **No
harm done and the process was still wrong**, and the only reason I can say the
first half with confidence is that T14.17 wrote down what was shown for each one.
That is the feature justifying itself on its first real outing, against its
author.

### The standing question this leaves

An audit-shaped task generates asks at a rate no per-call consent surface can
absorb — 16 for one question, all read-only, all inside the project. That is the
measured case **I18** (the persistent grant) exists for, and it is now a number
rather than an intuition. It stays frozen; it is the maintainer's call. But the
friction log can no longer say nothing has asked for it.
