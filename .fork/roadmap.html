3

Diagnose ambiguous_target on restored multi-tab profiles

done · 2026-09-12
effort: smallimpact: medium

Turned out not to be the judgment call it looked like. Diagnosis: every tab has exactly one is_active pane structurally (a PaneGroup invariant, not a restore artifact), so N tabs give N actives. The real bug was in session_inspect's defaulting: its old helper only widened window/tab/pane to Active when the caller had already passed session: Active explicitly, and was a no-op for the argument-less case — the one this whole complaint is about — leaving pane selection unscoped across every tab before the session-level filter ran. Reproduced live against two real tabs (ambiguous_target), fixed with a defaulting function scoped to session_inspect alone (not the shared helper, which session_list still needs its old "list everything" meaning from), confirmed live post-fix resolves to exactly the active tab's session, and confirmed an explicit --session <id> for a session in a non-active tab still finds it — a regression the first draft of the fix would have introduced by widening tab unconditionally. Four unit tests calibrated by breaking twice, each reddening only the test it targets. 8/8 metadata tests, 53/53 fork::, 181/181 local_control:: pass.

Source: this session, 2026-09-12; app/src/local_control/handlers/metadata.rs, live-tested via a scratch profile.
