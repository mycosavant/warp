A Conversation in Your Pocket

What the fork's /remote-control is today, what Claude Code's does that ours does not, and the smallest set of changes that closes the gaps worth closing. Four decisions were the maintainer's; each was answered with its recommendation on 2026-09-06 (.fork/decisions/2026-09-06-the-phone-surface-four-decisions.md), and one of them gates two of the others. The work is handed off in .fork/HANDOFF-MOBILE.md.

The shape, unchanged

A person at the keyboard points at one conversation and hands it to a phone. The phone gets that conversation and nothing else: it watches the record live, answers its permission requests, stops a turn, and sends the next prompt. Everything below is either a way to make that one gesture better or is refused because it would change what the gesture means.

The gaps, ranked by what a day with it would hit first

1

A real phone, once

measureno coderemote-control.md, "Unverified"

Every measurement so far had Brave on the Windows side standing in for the phone. Scan the block with a phone, install the page from the browser's menu (the manifest already says standalone), lock the phone mid-turn, unlock it, answer a request. The reconnect path and the 5-minute credential turnover have only been exercised by a browser that never sleeps.

expect

the QR block's text column clipped on a narrow pane (seen), and Chrome offering "add to home screen" as a shortcut rather than an install, because over plain HTTP the page does not meet its install criteria. iOS adds it either way, and gives it nothing a shortcut lacks.

2

Being told

console.jspage only, first half

The reason to have a phone in the loop is to be somewhere else while the agent works, and a page that has to be open and looked at gives up most of that. Two halves with very different costs.

The precondition is item 3. Every browser withholds the Notification API, service workers and push from a page that is not a secure context, and a secure context is https:// or the browser's own machine; http://192.168.254.3 is neither, and a tailnet address over plain HTTP is not either, however encrypted the tunnel under it. So nothing in this item can be built until the phone trusts the console's certificate. Vibration is the one thing not withheld.

Foreground. With that in place: while the page is open or installed and in the background of a phone that is awake, the Notification API and vibration fire on a new permission request and on a turn ending. No relay, no new server code: the events stream already carries both. Android Chrome does this from an installed page; iOS does it only from an installed page and only on 16.4 or later.

Background. A locked phone needs Web Push, and Web Push means the phone's browser subscribes at Google's or Apple's push service and Warp posts a nudge there. The payload is encrypted end to end by the standard, so the relay sees an opaque blob, an endpoint, and a timestamp. That is not nothing: it is a third party learning that this machine had something to say at 03:12. It is also the only way a locked phone buzzes.

decided
  • Foreground now, push never by default. Build the first half. Record the second as an opt-in behind its own variable, off, with the disclosure above beside it, and build it only if a week of use says the foreground half is not enough.
  • Both now. Push as opt-in from the start. Costs a VAPID key pair on disk, a subscription store, one more egress host to allow, and the first hole in "nothing leaves the machine" that is not a vendor deny-list.
  • Neither. SSH from Termux and a watcher script is the pure route and already works; accept that the console is for when you are looking at it.
3

The wire, twice: trust and reach

mod.rs, console.rsrustls, rcgenmanual.md, "Reaching this machine from a phone"

Two different problems that one sentence used to cover. Trust is whether the phone's browser believes the console is who it says, and it decides more than confidentiality: without it there is no secure context, so no notifications, no install, no service worker, and the token and every approval payload are readable on the wire. Reach is whether the phone can find the machine from outside the LAN at all.

Trust needs a certificate the phone accepts, and the fork can mint its own. A self-signed server certificate is a warning page and a tap-through, and nothing a QR carries can pin it. A fork-minted CA is different: Warp mints a CA key once, keeps it private in state_dir like the discovery record, signs a certificate for the bind address with it, and serves the CA's public half at one more constant route. The phone installs that CA once, from a link the pairing page shows, and from then on https://192.168.254.3:41234 is a secure context with no warning. Android installs a user CA from settings and Chrome honours it; iOS installs it as a profile and asks once more under certificate trust settings. It is the shape of a home router or a self-hosted service, nothing leaves the machine, and it is the only route that does not put a public DNS name in the loop. Cost: TLS on the axum listener (rustls), key and certificate minting (rcgen), the route, and a first-run step on each phone. The loopback listener stays plain, because warpctrl is not a browser and localhost is already a secure context.

Reach is the mesh, unchanged from the manual. A tailnet address is one literal IP that fits WARP_FORK_CONTROL_BIND, opens no inbound port and retires the firewall rule; Tailscale's coordination server is an account, so headscale on a small VPS replaces exactly that part. It does not give the browser a secure context, which is why it is the second half and not the whole.

decided
  • A fork-minted CA now; headscale when you have an evening. Trust is code and unblocks items 2 and 1's install; reach is ops and unblocks leaving the house. They do not wait on each other.
  • headscale first, CA later. Encrypts the wire sooner, notifications later; the phone stays a couch device that cannot be told anything meanwhile.
  • Stay on the LAN, plain. Honest and free. It means the console is for when you are looking at it, and item 2 is off the table.
4

How long a handed conversation stays handed

pairing.rsone constant and a rule

A device paired by pair show dies after 12 hours, which is the right lifetime for a weak credential minted by a variable. A device paired by the chip was minted by a person pointing at a conversation, and 12 hours means a run started at breakfast asks you to walk back to the machine at dinner to keep watching it. Meanwhile the credential map already voids everything confined to a conversation the moment you click Stop sharing, so the clock is not what bounds a leak; the confinement is.

decided
  • A control pairing lives as long as the conversation. It ends on Stop sharing, on the conversation being deleted, or on Warp closing, and on no clock. The watch pairing keeps its 12 hours. This is the reading that makes the gesture mean what it says.
  • Keep 12 hours everywhere. Simplest; the cost is the walk to the machine, once a day, for a run that is still going.
  • A longer clock, say 72 hours, for control only. A middle that has to be explained; it bounds nothing the confinement does not already bound.
5

The desk should know what the phone did

remote_control_block.rsevent_logsmall

Today the block shows a QR and the chip reads Stop sharing from the moment a code exists, whether or not anyone ever scanned it. Three things it should say and does not: paired at 14:02 when the code is spent, expired, click again when two minutes pass unscanned (the chip already flips back; the block keeps showing a dead code), and which prompts and answers came from the phone.

Where the provenance goes is a choice. Claude Code shows phone-sent messages in the local conversation as ordinary messages, and that is right for the conversation: they are your words. The record is where the origin belongs, and the event log already has an answered_by on permission replies that the console could fill; a prompt line wants the same field.

decided
  • Record it, do not mark it. prompt_submit and permission_replied carry via: paired_device in the event log; the conversation shows the prompt as yours; the block in the pane shows paired and expired states. The trace view then shows a small "from the phone" stamp on those rows, which is the record drawn, not the conversation edited.
  • Mark it in the conversation too. A prefix on the prompt in the panel. Cheap, but it puts a Warp aside in the agent's context, which the transcript work went to some trouble to avoid.
6

What the record shows

console.jstrace_render.rspage only

Three things the phone has in hand and does not draw. The mode and model in force are on the record's session_mode and session_model lines and belong in the conversation header, since "is the agent asking me or its classifier" is the first thing a phone wants to know. The working directory is on the first line. And an edit tool's input holds old and new text, which is a diff that is currently drawn as two strings; drawing it as a diff is the one thing Claude Code's phone view has that ours would visibly lack, and it is a render change on rows the page already has.

recommend

Build all three, in that order; none needs the desk to change. Header first, because it is an hour and it answers the question the trace's zero-request case already warns about.

7

More than one conversation on one phone

console.jslater

A phone that scans two codes holds the second and forgets the first, because the page stores one device. Holding several is a page change: a map of pairings keyed by conversation, a list to pick from, each with its own token and scope. The server side needs nothing; it already allows eight devices. Not urgent, because the honest use is one long run at a time, and the watch pairing from pair show already gives the overview for free.

Refused, and why

  • Start a new conversation from the phoneThe code was minted for one conversation by someone pointing at it. A new one was pointed at by nobody. The watch pairing does not get it either, for the same reason it never got agent.prompt.
  • Change the agent's permission mode from the phoneThe mode is the agent's, and the fork discloses it rather than choosing it (WARP_FORK_ACP_MODE has no default on purpose). Widening what the agent may do unasked is a policy change, and a QR code is the weakest credential in the system. Claude Code's phone does not document this either.
  • Answer for every agent from a control pairingThat is WARP_FORK_REMOTE_APPROVE, a different claim with its own switch. A control pairing answers its conversation's requests and no other's; this is what the pinned test holds.
  • A self-signed server certificate without a CAA warning page and a tap-through on the phone, which teaches the habit that lets a real attacker through, and nothing a QR carries can pin it. A CA the phone installs once is the version that works, and it is item 3.
  • A public certificateACME needs a DNS name the world can resolve pointing at this machine, or a DNS-01 challenge through a provider's API: a public name and an account for a console that is meant to be findable by one phone. The fork-minted CA is smaller and stays home.
  • Push by defaultSee item 2. An opaque nudge to a third party is still a third party learning when this machine had something to say.

Sequence, if the recommendations stand

  1. firstA real phone; fix the block's layout; note what iOS refuses.
  2. thenThe fork-minted CA and TLS on the wide listener; block states; provenance in the record; control pairing without a clock.
  3. thenForeground notifications; header with mode, model, cwd; edits as diffs.
  4. opsheadscale on a VPS; bind the tailnet address; retire the firewall rule.
  5. laterSeveral pairings on one phone; push as a disclosed opt-in if a week says so.

Step 2 is two days with the certificate work, step 3 a day, and each is measured the way the last two runs were: the phone's side from curl.exe, the desk's side from screenshots, and a run directory that keeps the driver.
